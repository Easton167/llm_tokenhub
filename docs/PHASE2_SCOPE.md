## 1. 二期目标

一期已验证核心商业闭环（个人 Key 调用 → 鉴权路由 → 转发 → 预扣实扣 → 用量记录）。二期的目标是把平台从「个人可用」推进到「组织可付费使用」：

```text
组织可以充值组织钱包并给成员分配额度，成员以组织身份调用模型并按额度受控扣费；
个人用户可以在线支付充值；运营可以看到成本/收入/利润级别的报表。
```

二期成功标准：

- 一个组织 Owner 可以创建组织、邀请成员、给组织钱包充值、给成员设置额度。
- 成员用自己的 API Key 以组织身份调用模型，费用从组织钱包扣除并累计到成员额度。
- 个人用户可以通过在线支付完成充值，支付回调幂等、可对账。
- 运营后台可以看到按模型/用户/组织/渠道维度的成本、收入、毛利报表。
- 平台对外提供 `/v1/embeddings`，并接入至少 1 个非 OpenAI-compatible 私有协议厂商。
- API Key 可以配置模型范围和 RPM/TPM 限额，超限返回标准 429。

## 2. 一期基线与遗留缺口

二期规划基于以下代码现状（2026-07 盘点）：

| 项 | 现状 |
| --- | --- |

## 3. 二期用户故事

| 编号 | 用户故事 | 验收标准 |
| --- | --- | --- |
| P2-U1 | 作为用户，我可以创建组织并成为 Owner | 创建后自动生成组织钱包，创建者为 Owner |
| P2-U2 | 作为组织 Owner/Admin，我可以邀请和移除成员并设置组织内角色 | Owner/Admin/Member 三级角色生效；移除成员不影响历史流水 |
| P2-U3 | 作为组织 Owner，我可以给组织钱包充值并查看组织流水 | 组织流水只追加，可关联 request_id 和发起成员 |
| P2-U4 | 作为组织 Admin，我可以给成员设置消费开关和额度上限 | 支持总额度和周期额度（每月），周期到期自动重置 |
| P2-U5 | 作为组织成员，我可以以组织身份调用模型 | 组织余额与成员剩余额度取更严者校验；扣组织钱包并累计成员已用额度 |
| P2-U6 | 作为用户，我可以为 Key 或单次请求选择计费主体 | Key 绑定默认主体；请求头 `X-Billing-Subject` 可覆盖；无权时 402/403 |
| P2-U7 | 作为个人/组织付款人，我可以在线支付充值 | 支付回调幂等；同一支付单重复回调不重复入账；支付单可对账 |
| P2-U8 | 作为运营，我可以查看成本/收入/利润报表 | 按天/模型/用户/组织/渠道维度出数；**收入 = 现金支付 `cash_revenue_amount`**（计费总额 `revenue_amount` 含赠金，不是收入）；毛利 = 现金收入 - 上游成本 |
| P2-U9 | 作为用户，我可以调用 `/v1/embeddings` | OpenAI 兼容请求/响应，按输入 token 计费 |
| P2-U10 | 作为管理员，我可以接入非 OpenAI 协议的厂商 | 至少 1 个私有协议适配器（建议 Anthropic 或 Gemini 原生协议）走通流式+非流式 |
| P2-U11 | 作为管理员，我可以限制 Key 的模型范围和速率 | Key 可配置允许模型列表和 RPM/TPM，超限返回 429 `rate_limit_exceeded` |

## 4. 二期功能边界

### 4.1 组织与成员（新模块）

包含：

- 组织 CRUD（创建、编辑、停用）。
- 成员邀请/移除、组织角色（Owner / Admin / Member）。
- 成员额度：消费开关、总额度/周期额度（按金额）、已用累计、周期自动重置。
- 前台「我的组织」页面，后台「组织管理」页面。

不包含：

- 组织间转账、组织层级（子组织）。
- SSO/企业目录同步。

### 4.2 组织钱包与计费主体

包含：

- 组织钱包（`wallets.owner_type = 'org'`），复用现有 hold/capture/release 链路（含赠送池，扣减顺序 赠送 → 现金 → 授信）。
- 扣费主体决策（按 `prd/wallet.md` 流程图）：请求显式指定 > Key 绑定主体 > 账户默认策略；组织消费需同时校验组织余额与成员额度；按策略回退个人或 402 拒绝。
- 请求头 `X-Billing-Subject: org:{org_id}` / `user:{user_id}` 动态指定。
- 组织扣费流水记录实际发起成员，支持费用分摊查询。
- `request_logs.billing_subject` 落真实值。

不包含：

- 透支/授信额度（三期）。
- 自动充值（三期）。

### 4.3 在线支付

包含：

- 支付单表（订单号、金额、状态机：created → paid / expired / failed）。
- 至少 1 个支付渠道（建议先支付宝或 Stripe，二选一落地，接口抽象支持扩展）。
- 回调验签 + 幂等入账（同一支付单只产生一次钱包流水）。
- 支付单与钱包流水对账任务（复用 `reconcile_holds` 的任务框架）。
- 前台充值页（个人钱包、组织钱包），后台支付单查询。

不包含：

- 退款到支付渠道（先支持后台调账）。
- 发票、套餐包、订阅制。

### 4.4 报表与运营看板

包含：

- 渠道成本价配置（渠道/模型维度的上游成本单价），用于毛利计算。
- 日粒度聚合表（按 天 × 模型 × 用户 × 组织 × 渠道 预聚合，定时任务写入）。
- 后台报表 API + 页面：收入/成本/毛利趋势、Top 用户/组织/模型、渠道成本占比。**收入口径为现金支付**；赠金消耗单列，不计入毛利。
- 用户/组织侧自助用量报表（按天汇总；含赠金/现金拆分）。

不包含：

- 实时大盘（分钟级）、自定义报表构建器。

### 4.5 对外能力扩展

包含：

- `POST /v1/embeddings`（OpenAI 兼容，按输入 token 计费，`models.model_type = 'embedding'`）。
- 至少 1 个私有协议适配器（Anthropic Messages 或 Google Gemini），适配器由 `model_channel_map` 所属渠道的 provider 类型选择，替换当前硬绑定 `openai_compatible_adapter` 的做法。
- rerank 视排期作为可选项（`POST /v1/rerank`，Cohere 兼容结构）。

不包含：

- `/v1/images/generations`、Assistants/Responses API。
- Function calling 完整兼容验证（保持透传）。

### 4.6 Key 级模型范围与限额

包含：

- `api_keys` 增加：允许模型列表（空=继承角色授权）、RPM/TPM 限额、可选过期时间。
- 网关侧限流执行（Redis 滑动窗口或令牌桶；无 Redis 时进程内降级）。
- 超限返回 OpenAI 兼容 429 `rate_limit_exceeded`，带 `Retry-After`。
- `channel_keys.rpm_limit/tpm_limit` 同步纳入路由选择（打满的 Key 降权/跳过）。

不包含：

- 用户级/组织级全局配额（除成员金额额度外）、按并发数限流。

### 4.7 权限与数据隔离增强

包含：

- 组织角色与平台角色并存：平台角色管模型授权，组织角色管组织内资源。
- 组织数据隔离：成员只能看本组织的用量/流水；后台按组织维度筛选。
- 组织敏感操作（充值、额度调整、成员变更）写入审计日志。

不包含：

- 多租户物理隔离、私有化交付（三期）。

新增表（详细 DDL 进 `DATABASE_DESIGN.md` 后再开发）：

| 表 | 说明 |
| --- | --- |

- `wallets`：启用 `owner_type='org'`（`owner_id` 指向 `orgs`）。

- `request_logs` / `usage_logs` / `wallet_transactions`：补充 `org_id`、发起成员字段。

## 6. 交付顺序（里程碑）

依赖关系：组织钱包是成员额度和计费主体的前置；报表依赖成本价配置；支付相对独立。

| 里程碑 | 内容 | 出口标准 |
| --- | --- | --- |
| M1 组织域基础 | 组织/成员/组织角色 CRUD + 组织钱包（后台手工充值） | 组织钱包可充值、可查流水 |
| M2 组织扣费闭环 | 计费主体决策、成员额度校验与累计、周期重置、回退策略、请求头指定 | 成员以组织身份调用成功扣组织钱包；额度超限 402；并发不超扣 |
| M3 在线支付 | 支付单、回调幂等、充值页、对账任务 | 沙箱环境完成支付→入账→对账全链路 |
| M4 报表 | 成本价配置、日聚合任务、后台报表页 | 收入/成本/毛利与流水对账一致 |
| M5 能力扩展 | embeddings 端点、1 个私有协议适配器、Key 级范围与限流 | embeddings 计费正确；私有协议流式走通；限流 429 生效 |

M1→M2 严格串行；M3、M4、M5 可在 M2 后并行排期。

具体开发任务拆分见 [`AI_TASK_BREAKDOWN_PHASE2.md`](./AI_TASK_BREAKDOWN_PHASE2.md)。

## 7. 验收口径

二期进入下一阶段的最低验收口径：

- 组织成员以组织身份调用 `/v1/chat/completions`，组织钱包产生 hold/capture 流水且记录发起成员。
- 成员额度耗尽后：配置回退个人则从个人钱包扣费，否则返回 `402 insufficient_balance`。
- 组织余额与成员额度并发竞争下不超扣（复用行级锁/原子更新口径）。
- 同一支付单回调重复送达 3 次，钱包只入账 1 次。
- `X-Billing-Subject` 指定无权主体时返回 403，不产生任何资金变动。
- Key 超过 RPM 限额返回 429，且不预扣、不调用上游。
- `/v1/embeddings` 成功请求产生 usage log 并按 embedding 计费规则扣费。
- 报表页「平台收入」合计与钱包 capture 流水的**现金部分**对得上；计费总额（含赠金）与 `Σ charge_amount` 对得上。赠金消耗与 capture `gift_amount` 对得上。

## 8. 变更控制

若开发中出现以下情况，应先更新本文档和 `TECH_DESIGN.md`，再继续写代码：

- 要引入套餐包、订阅制或授信透支。
- 要把赠送金与充值现金混回同一个 `balance`，或把赠金计入平台收入。
- 支付要支持多渠道并行或分账。
- 组织要支持层级（子组织）或跨组织共享额度。
- 要引入分钟级实时大盘或自定义报表。
- 私有协议适配器超过 2 个且协议差异需要改动 Adapter 抽象。
