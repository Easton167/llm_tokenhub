# 计费规则

> 模块 / 菜单：后台 · 计费规则  
> 返回 [PRD 索引](../PRD.md)

> **已确认基线（D1）**：MVP / 一期采用**纯按量计费（pay-as-you-go）**，按 Token / 按次实时结算；不做套餐包 / 订阅制。阶梯价若需要，后续迭代再评估。  
> **计费触发（D3）**：仅对**成功 / 部分成功**的请求计费；失败请求不计费。

---

## 功能点

- 每个模型独立配置计费规则，支持多计费维度：
  - **按 Token**：输入单价、输出单价、缓存命中输入单价、推理/思考 token 单价（可选）。
  - **按次 / 按请求**：固定每次调用费用（适用于部分图像/工具类模型）。
- 倍率（Multiplier）：在上游成本基础上的定价系数，区分「成本价」与「售价」，便于利润核算。
- 折扣：面向角色/组织的折扣率（如 VIP 0.8 折）。
- 计价单位：单价统一以**每 1M tokens**为单位存储，避免精度问题。
- 最小计费单位与取整规则：金额以**最小货币单位（如厘 / 0.0001 元）**存储，结算向上取整到最小计费单位。
- 货币与生效时间：支持币种、规则版本与生效时间（保留历史版本，按调用时间命中对应版本）。

### 管理端操作

| 操作 | 说明 |
| --- | --- |
| 新建规则版本 | 为模型新增一条规则；`version` 自动递增；新建后默认启用。 |
| 列表 | 按模型列出全部版本（含已作废），按 `version` 降序。 |
| 删除（作废） | **软删除**：将规则 `status` 置为作废，使其不再被新请求命中；**禁止物理删除**，保留记录供对账与审计。作废后历史账单仍按调用当时命中的版本解释，不受影响。 |

- 已作废规则不可再启用为同一版本；若需恢复定价，应**新建更高版本**并设置正确的 `effective_at`。
- 作废当前唯一启用规则后，该模型将无可用计费规则，调用会被拒绝（见「边界与异常」）。

### 后续可选：阶梯价（非一期）

按累计用量落入不同档位适用不同单价；累计口径按计费主体（个人 / 组织）+ 模型；统计周期支持自然月等。与 D1 冲突，**暂不实施**，仅作后续评估参考。

## 计费维度

| 维度 | 适用 | 计费方式 |
| --- | --- | --- |
| 输入 Token | chat/embedding | `input_tokens × price_input / 1e6` |
| 输出 Token | chat | `output_tokens × price_output / 1e6` |
| 缓存命中输入 Token | 支持 prompt 缓存的模型 | `cached_tokens × price_cached_input / 1e6` |
| 按次 | 图像/工具类 | `price_per_call` |
| 组合 | 混合模型 | 按次 + 按 Token 叠加 |

## 定价构成

```
售价单价 = 上游成本单价 × 倍率(multiplier)
最终费用 = 基础费用 × 角色/组织折扣
最终费用 = 向上取整到 min_charge_unit
```

- `multiplier` 体现平台利润；`cost_*` 字段用于成本与利润核算（利润 = charge_amount - cost_amount）。
- 计费规则版本化：按「请求发生时刻 `effective_at` 命中的版本」计算，历史账单不受新规则影响。

## 关键规则

- 费用计算（按 Token）：
  `费用 = (输入tokens×输入单价 + 输出tokens×输出单价 + 缓存tokens×缓存单价) / 1e6 × 倍率 × 折扣`
- 金额运算全程使用整数（最小货币单位）或 `Decimal`，禁止浮点累计误差。
- 取整规则：单次结算金额向上取整到 `min_charge_unit`（保证不亏计）。

## 示例计算

> 设货币最小单位为 0.0001 元（即 1 元 = 10000 单位）。模型 `gpt-4o` 计费规则（每 1M tokens，单位：元）：
> - 输入单价 = 18 元/1M，输出单价 = 72 元/1M，缓存命中输入 = 9 元/1M
> - 倍率 multiplier = 1.2（成本：输入 15 元/1M、输出 60 元/1M）
> - 折扣：pro 角色 1.0，VIP 0.9
> - min_charge_unit = 1 单位（0.0001 元）

### 示例 A：普通 chat 调用（pro 用户，无缓存）

- 实际用量：输入 1500 tokens，输出 800 tokens，缓存 0。
- 输入费用 = 1500 × 18 / 1e6 = 0.027 元
- 输出费用 = 800 × 72 / 1e6 = 0.0576 元
- 小计 = 0.0846 元；折扣 1.0 → 0.0846 元
- 取整到 0.0001 → **0.0846 元（846 单位）**
- 上游成本 = 1500×15/1e6 + 800×60/1e6 = 0.0705 元
- 平台利润 = 0.0846 - 0.0705 = **0.0141 元**

### 示例 B：命中缓存（VIP 用户，0.9 折）

- 实际用量：输入 2000 tokens（其中缓存命中 1600，非缓存 400），输出 500 tokens。
- 非缓存输入 = 400 × 18 / 1e6 = 0.0072 元
- 缓存输入 = 1600 × 9 / 1e6 = 0.0144 元
- 输出 = 500 × 72 / 1e6 = 0.036 元
- 小计 = 0.0576 元；VIP 折扣 0.9 → 0.05184 元
- 取整到 0.0001（向上）→ **0.0519 元（519 单位）**

### 示例 C：预扣 vs 实扣

- 请求 `max_tokens=2000`，输入估算 1500 tokens。
- 预扣估算 = 1500×18/1e6 + 2000×72/1e6 = 0.171 元 → 冻结 1710 单位。
- 实际输出仅 800 tokens，实扣 = 0.0846 元（846 单位，见示例 A）。
- 结算：释放 1710 - 846 = 864 单位回余额。

## 赠送余额抵扣与收入口径

> 赠送余额的发放、有效期与扣减顺序见 [钱包与流水 · 赠送余额](./wallet.md#赠送余额gift-credit)。

**计费金额本身不受资金来源影响**：无论用赠金还是现金支付，`charge_amount` 的计算公式、单价、倍率、折扣、取整规则完全一致。赠金只影响「这笔钱从哪个池扣」，不影响「这笔钱是多少」。

但**用量与账单必须区分资金来源**，因为收入口径不同：

| 指标 | 口径 |
| --- | --- |
| `charge_amount` | 本次调用应付总额（= 赠金抵扣 + 现金支付） |
| `gift_charge_amount` | 其中由赠送池抵扣的部分——**不是收入**，是营销费用的实际核销 |
| `cash_charge_amount` | 其中由现金池支付的部分——**这才是平台真实收入** |
| `cost_amount` | 上游成本，与资金来源无关，照付不误 |

- **真实毛利 = `cash_charge_amount - cost_amount`**。若沿用旧口径（`charge_amount - cost_amount`）会把送出去的钱算成收入，毛利虚高。
- 赠金消费部分的毛利必然为负（`0 - cost_amount`），这是**正常且预期**的营销投入，报表应单列「赠金消耗」与「赠金对应上游成本」两个指标，而不是混进毛利里。
- 约束：`gift_charge_amount + cash_charge_amount = charge_amount` 恒成立（整数拆分，不做比例分摊，避免 1 单位取整误差）。
- 日聚合表同步拆分 `gift_revenue_amount` / `cash_revenue_amount`。

### 示例 D：赠金与现金混合支付

- 承接示例 A（应付 846 单位），用户赠送池余额 300、现金池 5000。
- 预扣 1710 → 冻结 `gift 300 + cash 1410`。
- 实扣 846 → 退还 864，按逆序先退现金 864（现金实扣 546），赠送实扣 300。
- 记账：`charge_amount = 846`，`gift_charge_amount = 300`，`cash_charge_amount = 546`。
- 上游成本 705；**真实毛利 = 546 - 705 = -159 单位**（本次为营销净投入），而非旧口径的 +141。

## 结算与对账

- 实时：每次请求结束即结算并写流水。
- 离线：定时聚合 `usage_logs` 生成日/月账单（按用户、组织、模型、资金来源维度），与流水对账。
- 异常：未结算冻结超时释放；实扣失败重试，幂等基于 `request_id`。
- 赠金对账：每日校验 `Σ(active 批次 remaining) == wallets.gift_balance + wallets.gift_held`，以及 `Σ gift_charge_amount == Σ 赠送池 capture 金额`，不一致告警。

## 失败请求处理（D3）

- **不计费场景**：鉴权失败、权限不足、无可用渠道、上游错误（重试后仍失败）、请求参数错误等——一律**不计费**，预扣冻结额度**全额释放**，仅记录 `request_logs`（`status=failed`），不写计费用量。
- **部分成功（流式中断）**：若已向用户产出部分内容，按**已实际产出的 token** 计费，`status=partial`。
- **幂等保证**：释放与结算均以 `request_id` 幂等。

## 边界与异常

- 模型无计费规则：默认拒绝调用并告警，避免漏计费。
- 上游未返回 usage：按「输出按 max_tokens、输入按本地分词估算」兜底，并标记为估算记录。
