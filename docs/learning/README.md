### 先确认你的起点（30 秒）

打开 `backend/app/db/session.py`，看第 54–68 行的 `get_db()`。

- **能说清「`yield session` 后面那句 commit 什么时候执行」** → 起点合适，从阶段 1 开始。
- **看得懂每个单词但说不清整体在干嘛** → 先做 [阶段 0.5 前置补课](./stage-0-prerequisites.md)，8–12 小时，做完再回来。这不是绕路，跳过它后面每个阶段都会卡。

阶段 1–9 的时长是按「3 个月 Python + 会 FastAPI 语法」估的。**如果你是自学半年左右**，前三个阶段按 1.5 倍时间安排，第 4 阶段之后会自然追上来。

### 三条主线

细则不是九个孤立的文件，读的时候留意这三条贯穿全程的线：

- **资金线**：阶段 4（hold/capture/release）→ 阶段 5（钱包与支付）→ 阶段 6（双资金池）→ 阶段 8（向量化计费复用同一套）
- **抽象线**：阶段 4 适配器 → 阶段 5 支付抽象 → 阶段 8 存储抽象，**同一个模式出现三次**
- **兜底线**：阶段 5 对账任务 → 阶段 6 赠金对账 → 阶段 7 日聚合与调度 → 阶段 8 worker 队列

## 二、四种读代码的方式（后面每条读单都会标）

细则里每条阅读任务都标了一个模式字母，含义如下。**不要用同一种方式读所有文件**，这是新手读不动大项目的主要原因。

> **动手之前，永远先做这三件事**（30 秒，能省你半小时）：
> 1. 读文件**顶部的 docstring**。本项目几乎每个文件开头都有中文说明，写清了职责、设计取舍和坑。**它比任何外部讲解都准**。
> 2. 按 `Ctrl+Shift+O` 看符号大纲，先知道这个文件有几个函数、叫什么。
> 3. 问自己一句：「**这个文件不存在的话，会缺什么？**」带着这个问题读，比逐行扫有效得多。

### S = 扫读（每个文件 5–10 分钟）

只看三样东西，**不看函数体**：

1. 文件顶部 docstring
2. 所有 `def` / `class` 的**签名**和它上面那行注释
3. 模块级常量

产出：一句话说清「这个文件负责什么、对外暴露哪几个函数」。写不出这一句话就是没扫完。

### Q = 提问精读（每个文件 20–40 分钟）

**带着具体问题读，读完必须能书面回答。**问题在每条读单里已经给你写好了。

标准动作：

1. 把问题抄进笔记，**每题下面先写一句你的猜测**（哪怕是瞎猜）。这一步不能省：没有猜测的阅读留不下东西。
2. 读代码时只找与问题相关的分支，其他分支先跳过。**允许有大片代码这一轮完全不看。**
3. 写下答案，**必须附「代码依据：文件:行号」**。写不出行号 = 你其实是在复述印象，不是在读代码。
4. 回头对比你的猜测和答案，差在哪就是你的真实收获，**把差异单独标出来**。

#### 完整示范：用 Q 模式读 `app/middleware/request_id.py`

第一次做 Q 模式容易走样，这里给一次逐步实录，照着模仿一遍就会了。

**第 0 步**，读 docstring（`request_id.py:1-9`）。它已经把职责列成了 5 条。**先把这 5 条抄进笔记**，这就是你的阅读地图。

**第 1 步**，抄下问题并写猜测：

```
Q: clear_request_context() 为什么在成功和异常两个分支各写了一次？
我的猜测：可能是复制粘贴冗余？（← 记下来，后面打脸）
```

**第 2 步**，只读相关代码。这里就是 `dispatch`（`:39-84`）的 try / except / else 三段。

**第 3 步**，写答案 + 行号：

```
A: 不是冗余。except 分支（:68）清完之后 raise 把异常继续抛出去，
   压根不会走到 else 分支（:83）。两条路径互斥，各自都必须清一次。
   代码依据：request_id.py:52-84
   如果漏掉 except 那一次：contextvars 残留，同一个 worker 协程处理下一个请求时
   日志会带上上一个请求的 request_id —— 排障时会看到「串号」。
```

**第 4 步**，对比猜测：我原以为是冗余，实际是 try/except/else 的控制流决定的。**这条差异说明我对 `else` 分支的执行条件理解不牢**——记下来，这是比答案本身更值钱的东西。

**第 5 步**，答不上来的题去问 AI。**问「为什么」，不要问「这是什么意思」**：

| 别这么问 | 这么问 |
| --- | --- |
| 这段代码什么意思 | 我理解成 X，对吗？如果不对，我错在哪一步 |
| contextvars 是什么 | 这里为什么用 contextvars 而不是全局变量？换成全局变量会出什么错 |
| 帮我解释 dispatch | `dispatch` 里为什么先 bind 再 `call_next`，顺序反过来会怎样 |

追问三连（万能，卡住时按顺序问）：**① 不这么写会怎样？② 换个常见写法有什么代价？③ 这个项目为什么选了现在这种？**

### T = 测试反推（每个测试文件 20–30 分钟）

先读测试再读实现，这是本项目最省力的入口——测试就是这个模块的「使用说明书」，而且**保证是对的**（它跑得过）。做法：

1. 只看测试函数名 + 最后几行的 `assert`，先不看 setup
2. 把「输入 → 期望输出」抄成一张表
3. 带着这张表回去读实现，看代码怎么满足每条断言

想确认自己读懂了：**故意改坏实现里的一行，跑测试，看哪个用例先红**。红的那个就是这行代码的存在理由。改完 `git checkout` 还原。

### B = 断点跟读（每次 30–60 分钟）

在 Cursor / VS Code 里真的跑起来单步走。**这是本手册里最重要的一种，一次胜过十遍静读。**

一次性配置（项目根目录 `.vscode/launch.json`，没有就新建）：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "FastAPI (backend)",
      "type": "debugpy",
      "request": "launch",
      "module": "uvicorn",
      "args": ["app.main:app", "--reload", "--port", "8000"],
      "cwd": "${workspaceFolder}/backend",
      "justMyCode": false
    },
    {
      "name": "Pytest 当前文件",
      "type": "debugpy",
      "request": "launch",
      "module": "pytest",
      "args": ["${file}", "-v"],
      "cwd": "${workspaceFolder}/backend",
      "justMyCode": false
    }
  ]
}
```

> `--reload` 在调试时偶尔会让断点失效，断点打不上就去掉 `--reload` 再试。
> `justMyCode: false` 必须有，否则你无法单步进入 FastAPI / SQLAlchemy 内部（阶段 1 需要）。

断点跟读的固定动作：
1. 打断点 → F5 启动 → 用 curl 或 Swagger 发一个请求
2. 命中后**先看 Variables 面板**，把关键变量的真实值抄进笔记（不是类型，是值）
3. `F10` 单步过、`F11` 单步入、`Shift+F11` 跳出
4. 用 Debug Console 直接执行表达式验证猜想，例如输入 `auth.user_id` 回车

**不会用调试器就先用 `print`**。在想看的那行上面插一句 `print("HERE", 变量名)`，跑一次看输出，效果的八成都有了。等你觉得 print 加得太累了，自然就会想学断点——那时候再学，5 分钟就会。

## 三、卡住了怎么办（每次卡壳都按这个来）

读不懂是常态，不是信号。**关键是别在一个点上耗超过 15 分钟。** 按顺序执行，哪一步解决了就停：

1. **先分清卡在哪一层**，三层的解法完全不同：

| 症状 | 卡在 | 怎么办 |
| --- | --- | --- |
| 这个**语法**没见过（`@`、`yield`、`Annotated`、`\|`） | Python 语法 | 去 [阶段 0.5](./stage-0-prerequisites.md) 查，或让 AI 给一个**不带 FastAPI 的**最小例子 |
| 语法认识，但不知道**谁在什么时候调它** | 框架机制 | 打断点 / 加 print，让程序告诉你，别猜 |
| 都懂，但不知道**为什么要这么设计** | 业务意图 | 去 `docs/prd/` 和文件顶部 docstring 找，再不行问 AI「不这么写会怎样」 |

2. **打个 print 跑一遍**。90% 的「不知道谁在什么时候调它」，一个 print 就结束了。
3. **去看这个模块对应的测试**（`backend/tests/`）。测试是可执行的说明书，比你脑补准。
4. **用 AI，但按 §二 的模板问**（带上你的猜测）。要「解释 + 最小例子」，**不要**「帮我改代码」。
5. **还是不行就打标记跳过**：在笔记里写 `TODO: 没读懂 xxx.py:NN`，继续往下。**很多疑问会在后面两个阶段自动解开**——比如「为什么 chat 要提前 commit」，阶段 1 想不通很正常，阶段 4 一看就懂。每个阶段结束回头清一遍 TODO 列表。

### 行号对不上怎么办

细则里写的 `xxx.py:NN` 是**写文档那一刻**的行号。代码改过之后会漂移，**这很正常，不是你找错文件了**。

对不上时：按 `Ctrl+Shift+O` 搜函数名，或 `Ctrl+Shift+F` 全局搜代码片段。**以函数名为准，行号只当粗略指路。**

### 三条止损纪律

- **单点卡壳不超过 15 分钟**，超了就打 TODO 跳过。
- **一次只追一个问题**。读 `main.py` 时冒出「Depends 怎么实现的」，写进 TODO，不要当场跳进 FastAPI 源码——那是无底洞。
- **允许「这个分支我这轮不看」**。项目里大量分支是给边界情况准备的，第一遍只读主干路径（happy path）。

## 四、环境速查（Windows / PowerShell）

```powershell
# 1. 进后端目录，激活虚拟环境（本项目 venv 在 backend/.venv）
cd d:\LLM_TokenHub\backend
.\.venv\Scripts\Activate.ps1

# 2. 依赖：PostgreSQL 必须起着（localhost:5432/tokenhub，见 backend/.env）
#    Redis 可选：连不上会自动降级为进程内限流，不影响大部分学习
psql -U postgres -h localhost -d tokenhub -c "select 1"

# 3. 迁移到最新
alembic upgrade head

# 4. 起服务
uvicorn app.main:app --reload

# 5. 跑测试（注意：测试连的是真实 Postgres，不是内存库）
pytest                              # 全量
pytest tests/test_openai_api.py -v  # 单文件
pytest tests/test_openai_api.py -k "stream" -v
```

几个必须知道的事实，能省你半天：

- **测试用真库**。`tests/conftest.py:32` 直接用 `settings.database_url` 建 engine，没有 sqlite 内存库。所以跑测试前 Postgres 必须能连。
- **`db_session` fixture 会回滚**（`conftest.py:34-38`），测试写入的数据不会留在库里。想手工看数据，要用真实 HTTP 调用而不是跑测试。
- **`asyncio_mode = "auto"`**（`pyproject.toml:47`），写 async 测试**不需要**加 `@pytest.mark.asyncio`。
- 改 `backend/.env` 后**必须重启服务**。原因见阶段 1。

## 五、贯穿全程的三条纪律

1. **练习一律开新分支**：`git checkout -b learn/stage1-health-detail`，练完 `git checkout main` 丢掉，不污染主干。
2. **AI 当老师不当枪手**：读不懂就问「为什么这么写、不这么写会怎样」；练习自己写完再让 AI review。让 AI 直接写练习 = 这个阶段白学。
   > 判断标准很简单：**AI 的输出是进你脑子还是进你的文件？** 进脑子（解释、最小例子、review 意见）随便用；进文件（帮我写这个接口）= 这个阶段白学。
3. **每个阶段必须过关**再进下一阶段。过关标准在每个细则文件的最后一节，是自测题形式，答不上来就回去重读对应的读单条目。

### 一次典型的学习 session 长什么样（2 小时）

第一次上手不知道怎么安排时间的话，照这个来：

| 时长 | 干什么 |
| --- | --- |
| 5 min | 翻开上次的笔记，看一眼上次留的 TODO |
| 10 min | 读本次读单条目的问题清单，**每题写一句猜测** |
| 50 min | 按模式字母读代码，写答案 + 行号（中间卡壳按第三节止损） |
| 10 min | 休息 |
| 40 min | 动手：断点跟一次 / 写几行练习 / 跑一次测试 |
| 5 min | 收尾：把没解决的写成 TODO，写一句「今天最大的收获是」 |

**最后那一句「今天最大的收获是」不要省。** 它是你判断这两小时有没有白花的唯一标准；连着两次写不出来，说明节奏太快了，退回去重读。
